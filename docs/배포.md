# 배포 (Firebase + Cloud Run)

백엔드는 Cloud Run, 프론트는 Firebase Hosting, 로그인은 Firebase Authentication(Google)을 쓴다.
`main`에 머지하면 GitHub Actions(`.github/workflows/deploy.yml`)가 Cloud Run에 자동 배포한다.

```
학생 브라우저
   │
Firebase Hosting ── 프론트
   │  /api/** → Cloud Run (같은 주소라 CORS 불필요)
Cloud Run ── 백엔드 (Dockerfile: 마이그레이션 적용 후 서버 시작)
   │
PostgreSQL (Neon 또는 Supabase 무료)
```

처음 한 번만 아래 순서로 설정한다. Firebase 프로젝트와 Google Cloud 프로젝트는 **같은 프로젝트**다.

---

## 1. Firebase 프로젝트

1. https://console.firebase.google.com 에서 프로젝트를 만든다.
2. 요금제를 **Blaze(종량제)**로 바꾼다. Cloud Run에 필요하다. 무료 사용량 안에서는 비용이 거의 없다.
3. **예산 알림**을 꼭 건다: Google Cloud 콘솔 → 결제 → 예산 및 알림 (예: 월 5,000원).
4. Authentication → 로그인 방법 → **Google** 사용 설정.
5. Authentication → 설정 → 승인된 도메인에 배포 주소가 있는지 확인한다 (`<프로젝트>.web.app`은 기본 포함).
6. 프로젝트 설정 → **프로젝트 ID**를 적어 둔다.

## 2. DB (PostgreSQL)

1. Neon(https://neon.tech) 또는 Supabase에서 무료 DB를 만든다. 리전은 서울과 가까운 곳(예: 싱가포르, 도쿄).
2. 연결 주소(`postgresql://...?sslmode=require`)를 복사한다. 그대로 넣으면 백엔드가 asyncpg용으로 바꿔 쓴다.
3. 이 주소는 비밀값이다. 코드, 채팅, 문서에 붙여 넣지 않는다.

## 3. Google Cloud 설정

Google Cloud 콘솔(https://console.cloud.google.com)에서 같은 프로젝트를 고른다.

1. API 사용 설정: Cloud Run, Cloud Build, Artifact Registry, Secret Manager
2. **Secret Manager**에 `DATABASE_URL` 비밀값을 만들고 2번의 DB 주소를 넣는다.
   - Cloud Run이 이 값을 읽도록, 실행 서비스 계정(기본값: Compute Engine 기본 서비스 계정 `<숫자>-compute@developer.gserviceaccount.com`)에 **Secret Manager 보안 비밀 접근자** 역할을 준다.
3. **배포용 서비스 계정**을 만든다 (IAM → 서비스 계정, 예: `github-deployer`).
   - 소스 배포에 필요한 역할을 준다. Cloud Run 공식 문서의 "소스에서 배포" 권한 항목을 확인한다.
     보통 Cloud Run 관리자, 서비스 계정 사용자, Cloud Build 편집자, Artifact Registry 관리자, 저장소 관리자가 필요하다.
   - 키 → 키 추가 → JSON으로 키 파일을 받는다. **이 파일은 비밀값이다.** GitHub에 등록한 뒤 PC에서 지운다.

## 4. GitHub 저장소 설정

backend 저장소 → Settings → Secrets and variables → Actions

| 종류 | 이름 | 값 |
|---|---|---|
| Secret | `GCP_SA_KEY` | 3번에서 받은 JSON 키 파일 내용 전체 |
| Variable | `GCP_PROJECT_ID` | 프로젝트 ID |
| Variable | `GCP_REGION` | (선택) 기본값 `asia-northeast3` (서울) |
| Variable | `CLOUD_RUN_SERVICE` | (선택) 기본값 `backend` |

`GCP_PROJECT_ID`를 등록하기 전에는 배포 단계를 건너뛴다. 그래서 설정 전에 머지해도 실패하지 않는다.

## 5. 첫 배포와 환경변수

1. Actions 탭 → Deploy → **Run workflow**로 첫 배포를 실행한다.
   - Cloud Run 서비스가 만들어지고, 서버가 켜질 때 DB 테이블이 자동으로 만들어진다 (`alembic upgrade head`).
   - `DATABASE_URL`(Secret Manager)과 `FIREBASE_PROJECT_ID`(GitHub 변수)는 워크플로가 넣는다.
2. 관리자 설정: Cloud Run 콘솔 → 서비스 → **새 버전 수정 및 배포** → 변수 및 보안 비밀

   | 이름 | 값 |
   |---|---|
   | `ADMIN_EMAILS` | 관리자 이메일, 쉼표로 구분 |
   | `ALLOWED_EMAIL_DOMAINS` | (선택) 허용 도메인, 쉼표로 구분. 비우면 모든 Google 계정 허용 |

   한 번 설정하면 이후 자동 배포에서도 유지된다.
3. 배포가 끝나면 서비스 주소의 `/docs`가 열리는지 확인한다.

## 6. 프론트 연결 (프론트 저장소 작업)

프론트의 `firebase.json`에서 `/api/**` 요청을 Cloud Run으로 넘긴다.

```json
{
  "hosting": {
    "public": "dist",
    "rewrites": [
      { "source": "/api/**", "run": { "serviceId": "backend", "region": "asia-northeast3" } },
      { "source": "**", "destination": "/index.html" }
    ]
  }
}
```

프론트는 Firebase SDK로 Google 로그인한 뒤, API를 부를 때마다 헤더에 ID 토큰을 붙인다.

```ts
const token = await auth.currentUser?.getIdToken();
fetch("/api/v1/users/me", { headers: { Authorization: `Bearer ${token}` } });
```

## 7. API 요약 (프론트 전달용)

| API | 설명 |
|---|---|
| `GET /api/v1/users/me` | 내 정보. **처음 호출하면 회원가입**된다. `isAdmin`으로 관리자 여부 확인 |
| `GET /api/v1/admin/users` | 전체 사용자 목록 (관리자 전용) |
| 로그아웃 | 백엔드 API 없음. 프론트에서 Firebase `signOut()` |

에러 코드: `UNAUTHORIZED`(401, 토큰 없음·잘못됨·만료), `FORBIDDEN`(403, 관리자 아님), `EMAIL_NOT_ALLOWED`(403, 허용되지 않은 도메인)

## 로컬 개발

```bash
cp .env.example .env      # FIREBASE_PROJECT_ID만 채우면 된다. DATABASE_URL을 비우면 SQLite(local.db)
uv run alembic upgrade head
uv run fastapi dev app/main.py
```

## 확인이 필요한 것
- Firebase Hosting을 거칠 때 스트리밍(SSE) 응답이 끊기지 않는지 (채팅 스트리밍 구현 때 확인)
- Cloud Run은 요청이 없으면 꺼져서 첫 요청이 몇 초 걸린다. 시연 전에 한 번 호출해 둔다.
